# 知识工程平台产品需求与原型评审说明书

> 文档版本：V0.1  
> 文档状态：产品需求底稿／原型评审稿  
> 适用范围：知识工程平台产品规划、原型评审、详细 PRD 编写、技术方案设计  
> 对应原型：`knowledge-engineering-platform-prototype/`

## 1. 文档目的

本文档用于固化知识工程平台已确认的产品逻辑、模块边界、业务流程和原型要求，作为后续编写详细 PRD、组织业务评审和进行技术架构设计的输入。

本文档不将原型中的示例数据、数量和机构名称视为最终业务定义。原型主要用于表达产品形态、信息架构和关键流程。

## 2. 建设背景与产品定位

### 2.1 建设背景

企业知识分散在数据库、业务系统、文档库、网页、对象存储、消息队列及个人经验中，存在来源分散、标准不一、版本不清、权限脱节、难以检索、难以复用和无法支撑 AI 应用等问题。

平台需要完成从“原始数据与文档”到“可信知识资产”，再到“图谱、检索、知识服务和 Agent 应用”的完整链路建设。

### 2.2 产品定位

知识工程平台定位为企业级知识基础设施和知识生产平台，而不只是文档库、搜索引擎、图数据库或 Agent 开发工具。

平台应同时具备以下能力：

- 统一纳管企业结构化、非结构化和多模态数据。
- 将原始数据加工为可理解、可审核、可发布的候选知识。
- 对知识的来源、版本、责任人、权限、质量和适用范围进行治理。
- 建设企业统一语义知识图谱和专题业务知识图谱。
- 通过全文、向量、图谱、结构化数据和业务规则的混合服务支撑上层应用。
- 为业务系统、AI 应用和 Agent 提供 API、MCP、Skill 等标准化能力。
- 建立可持续运营、质量闭环、问题反馈和效果评估机制。

## 3. 核心产品原则

### 3.1 知识资源不等于知识资产

采集进入平台的文档、数据表、网页和多媒体内容首先是“知识资源”。资源需经过解析、抽取、加工、质量评估和业务审核，确定其责任人、权威等级、适用范围和发布版本后，才能成为“知识资产”。

### 3.2 知识加工必须位于资产化之前

知识处理与加工的输出是候选知识，包括切片、摘要、关键词、实体、关系、事件、术语、问答对、向量及质量结果。候选知识不得在未审核、未发布的情况下默认成为正式资产。

### 3.3 图谱构建在产品主流程上位于资产中心之后

图谱构建应优先消费已经通过质量门禁、完成审核并发布的实体、关系、事件、术语和规则类知识资产。不应将“从原文抽取实体关系”与“将已确认资产映射为图谱”设计为同一个不可分辨的步骤。

需同时保留“本体模型指导知识抽取”的能力，但这属于模型对加工环节的前置指导，不改变正式构图应使用发布资产的原则。

### 3.4 权限与来源证据贯穿全链路

原始权限应在采集时同步获取，并在资源、加工产物、知识资产、图谱、索引、服务和 Agent 应用中继承或按规则重新授权。任何知识结果都应可追溯至来源资源、原文位置和处理过程。

### 3.5 平台建设必须与业务场景结合

平台不能仅呈现技术能力清单。每个模块应回答“谁在什么业务流程中，使用哪些知识，完成什么任务，如何判断结果可信”。平台级通用能力应通过知识包、专题图谱、知识服务和场景 Agent 被业务使用。

## 4. 总体信息架构

平台一级产品模块确定为：

1. 知识采集
2. 知识资源管理
3. 知识处理与加工
4. 知识资产中心
5. 知识图谱构建与管理
6. 知识索引与服务
7. 知识应用与 Agent
8. 知识运营

主生产链路为：

`数据源 → 原始知识资源 → 候选知识 → 已发布知识资产 → 知识图谱／知识索引 → API、MCP、Skill → 业务应用与 Agent → 运营反馈`

运营反馈可触发资源补充、重新加工、资产修订、图谱更新和应用重新评测，形成闭环。

## 5. 分模块需求

### 5.1 知识采集

#### 模块目标

统一管理企业内外部数据源与采集任务，将数据持续、完整、可追溯地登记为原始知识资源。

#### 功能范围

- 数据源管理：名称、类型、连接信息、责任人、所属部门、安全级别、状态。
- 采集任务：创建、调度、暂停、恢复、重试、取消、执行记录。
- 同步方式：全量、增量、定时、实时。
- 接入方式：文件导入、API、数据库、对象存储、消息队列，后续可扩展企业内容平台和 SaaS 连接器。
- 原始权限获取：识别源系统的用户、组织、角色、密级和资源授权。
- 原始知识资源登记：为每项采集结果生成唯一标识并记录来源链路。
- 采集监控：资源数量、成功率、同步延迟、错误类型、SLA 告警。

#### 关键规则

- 数据源连接信息和凭证不得在页面中明文展示。
- 采集失败不得生成假的完整资源；部分成功需显式标记。
- 增量同步需保留水位、快照或偏移量，支持断点续传和重放。
- 删除源系统或采集任务时，不得默认级联删除已发布知识资产。

### 5.2 知识资源管理

#### 模块目标

统一管理已采集、但尚未必然成为知识资产的原始资源。

#### 功能范围

- 基础元数据：资源名称、类型、格式、大小、创建时间、更新时间、责任人。
- 来源系统与来源位置。
- 资源版本管理、变更识别与版本对比。
- 资源状态：待加工、加工中、已加工、部分失败、不完整、已失效等。
- 原始权限查看、异常识别和同步状态。
- 资源预览、下载、详情、血缘和历史版本查看。
- 批量选择资源并发起知识加工任务。

#### 边界说明

- 本模块管理“原始资源”，不承担业务目录、权威认定和知识发布。
- 技术元数据如数据库字段、文件格式和 Schema 属于资源层；业务语义、权威等级和适用范围主要属于资产层。

### 5.3 知识处理与加工

#### 模块目标

通过可配置、可编排、可重跑的加工流水线，将原始资源转化为带有证据、置信度和质量结果的候选知识。

#### 加工能力

- 文档解析。
- OCR 与多模态解析。
- 文档切片与上下文保留。
- 摘要和关键词生成。
- 实体、关系和事件抽取。
- 术语识别与候选术语生成。
- 问答对生成。
- 实体对齐、消歧和合并建议。
- 知识冲突识别。
- 向量生成与嵌入模型版本记录。
- 质量评估、阈值门禁和人工抽检。

#### 流水线要求

- 支持按业务域和资源类型建立加工模板。
- 支持节点级配置、执行、失败重试、跳过、人工介入和从指定节点重跑。
- 每个产物需记录输入资源、算法／模型版本、配置参数、执行批次和产出时间。
- 抽取结果需关联原文证据片段、页码、表格单元格或数据库记录。
- 自动通过质量门禁的结果仍为“待资产化候选知识”，不等同于已发布资产。

### 5.4 知识资产中心

#### 模块目标

将通过加工的候选知识进行业务审核、编目、授权、质量认定和发布，形成有责任主体、有来源、有版本、有适用范围的可信知识资产。

#### 功能范围

- 知识目录管理：企业级目录、业务域目录、专题目录、知识包。
- 业务元数据：业务定义、所属域、标签、业务对象、使用场景。
- 管理元数据：责任部门、责任人、审核人、保密级别、保留期、合规要求。
- 资产类型：文档、片段、术语、实体、关系、事件、规则、问答对、知识包等。
- 发布管理：草稿、待审核、已通过、已发布、已下线、已废止。
- 权限管理：继承源权限、资产独立授权、按组织／角色／用户／应用授权。
- 质量评定：完整性、准确性、一致性、时效性、可追溯性。
- 权威等级：用于表达来源权威性和冲突裁决优先级。
- 适用范围：全企业、指定业务条线、指定场景、指定应用、指定时间区间。
- 资产版本：版本号、变更说明、生效日期、失效日期、版本对比、回滚。

#### 资产准入条件

候选知识转为正式资产时，至少应确定：

- 唯一资产标识。
- 知识类型与所属目录。
- 来源资源和证据位置。
- 责任部门、责任人和审核人。
- 质量结果和权威等级。
- 适用范围与访问权限。
- 生效、失效和版本信息。
- 审核意见和发布记录。

### 5.5 知识图谱构建与管理

#### 模块目标

将已发布的实体、关系、事件、术语和规则资产映射到本体模型，建设可查询、可推理、可追溯的知识图谱。

#### 图谱分类

1. **企业统一语义知识图谱**
   - 范围：企业级、跨业务域、全局通用。
   - 目标：建立统一概念、术语、实体身份和跨域关系，支撑企业级语义检索和知识门户。
   - 特征：强调稳定性、共享性、语义标准和跨域复用。

2. **专题业务知识图谱**
   - 范围：某一业务场景、专项任务或特定应用。
   - 目标：围绕场景问题组织实体、关系、事件、规则和证据，支撑专题检索、分析、推理和 Agent。
   - 特征：强调场景适配、快速迭代和应用效果。

两类图谱的基本构建流程一致：

`本体建模 → 资产映射 → 构图任务 → 质量校验 → 人工确认 → 发布 → 可视化与服务`

两者的差异主要是知识范围、管理责任、变更节奏和上层应用场景，不应建设两套完全割裂的构图工具。

#### 功能范围

- 本体模型创建、继承、版本、审核和发布。
- 概念类、属性、关系类型、事件类型、约束和规则建模。
- 已发布资产与本体的映射、转换和同步规则。
- 全量构图、增量构图、定时更新、变更影响分析。
- 图谱质量检查：重复节点、孤立节点、关系冲突、约束违反、来源缺失。
- 图谱审核、发布、版本、回滚和环境管理。
- 图谱可视化、实体详情、关系路径、上下游追溯和来源证据查看。

### 5.6 知识索引与服务

#### 模块目标

将已发布知识资产和图谱封装为权限感知、可监控、可版本化、可复用的标准知识能力。

#### 功能范围

- 全文检索、向量检索、语义检索、图谱查询和结构化查询。
- 多路召回、排序、重排、去重、权威等级加权和时效性处理。
- 检索前权限过滤，而不是将无权内容召回后再隐藏。
- 检索结果返回资产版本、来源证据、原文定位和适用范围。
- 知识服务创建、测试、发布、版本、灰度、下线和调用监控。
- 服务封装形式：API、Graph API、MCP Server／Tool、Skill、RAG Context。
- 服务目录、在线调试、调用文档、密钥和应用授权。
- 服务可用性、调用量、延迟、错误率、权限拦截和成本监控。

### 5.7 知识应用与 Agent

#### 模块目标

将文档、知识资产、统一语义图谱、专题图谱、业务规则和系统工具组合为面向具体业务任务的知识应用。

#### 应用形态

- 企业统一语义检索。
- 专题知识图谱检索与分析。
- 企业语义知识门户。
- 制度问答、合同审查、风险分析等场景应用。
- Agent 构建和运行。
- 可插拔的应用模板与行业解决方案。

#### Agent 构建流程

`定义业务场景 → 选择知识资产与图谱 → 配置 Prompt／Skill → 编排 MCP／API 工具 → 配置权限与人工审批 → 建立评测集 → 灰度发布 → 运行监控与持续优化`

#### 安全与可信要求

- Agent 必须继承当前用户的知识访问权限。
- 高风险或产生外部状态变更的操作应支持人工审批。
- 问答和决策建议应展示来源引用、知识版本和适用范围。
- 需保留完整的输入、检索、工具调用、审批、输出和错误日志。
- 不同场景 Agent 应使用独立的知识范围、工具权限和评测标准。

### 5.8 知识运营

#### 模块目标

从知识供给、质量、使用效果、问题和成本角度建立持续运营闭环。

#### 功能范围

- 平台总览：数据源、资源、加工任务、资产、图谱、服务、应用。
- 质量运营：准确率、完整率、冲突率、过期率、无来源率。
- 使用运营：检索量、问答量、零结果率、点击率、引用率、用户反馈。
- 任务工单：知识缺失、知识冲突、知识过期、权限异常、索引异常、应用效果差。
- 责任分派、优先级、处理时限、进度跟踪、自动复测和关闭确认。
- Agent 评测、应用成功率、人工审批拦截、幻觉和越权风险监控。
- 资源、模型、向量、存储和调用成本分析。

## 6. 跨模块对象与状态

### 6.1 核心对象

- 数据源。
- 采集任务与采集批次。
- 原始知识资源与资源版本。
- 加工流水线、加工任务与节点执行记录。
- 候选知识与质量评估结果。
- 知识资产、资产版本、目录和知识包。
- 本体、图谱、构图任务和图谱版本。
- 索引、检索策略和知识服务。
- Skill、MCP Tool、API、应用和 Agent。
- 运营指标、用户反馈和治理工单。

### 6.2 建议状态链

| 对象 | 建议核心状态 |
| --- | --- |
| 知识资源 | 待加工、加工中、已加工、异常、已失效 |
| 候选知识 | 待评估、已通过、待抽检、待裁决、已驳回 |
| 知识资产 | 草稿、待审核、已通过、已发布、已下线、已废止 |
| 图谱 | 设计中、构建中、待校验、待发布、已发布、已归档 |
| 知识服务 | 草稿、测试中、灰度、在线、已停用 |
| Agent | 草稿、配置中、评测中、灰度、已发布、已停用 |

## 8. 全局非功能需求

### 8.1 安全与合规

- 支持组织、角色、用户、应用和数据密级的多维权限判断。
- 敏感知识需支持脱敏、水印、导出限制和调用审批。
- 保留采集、加工、审核、发布、权限变更、检索和 Agent 执行审计日志。
- 支持数据删除、资产下线、索引失效和图谱变更的一致性处理。

### 8.2 可追溯性

- 从搜索结果、图谱节点和 Agent 答案可追溯至资产版本、候选知识、加工批次和原始资源。
- 变更原始资源或资产时，应能分析对图谱、索引、服务和应用的影响。

### 8.3 可扩展性

- 采集连接器、解析器、抽取模型、向量模型、图数据库和检索引擎应支持可插拔扩展。
- 平台能力应优先通过稳定 API 与事件机制解耦。
- 不应将业务特定逻辑固化在企业级基础模型中。

### 8.4 可用性与性能

- 核心服务需建立 SLA，并分别定义批处理、交互检索和 Agent 调用的性能目标。
- 大批量加工、构图与索引任务应支持水平扩展、断点续跑和任务优先级。
- 交互页面应区分加载中、空数据、部分失败、无权限和系统异常状态。

## 9. 原型设计与交互要求

### 9.1 原型组织方式

- 该产品是系统性平台，不得将全部页面和逻辑集中在一个 HTML 文件中。
- 平台总览和八个一级模块应拆分为独立页面。
- 导航、顶栏、设计令牌、基础组件、公共样式和通用交互应共享复用。
- 后续每个一级模块应继续拆分列表、详情、创建／编辑、审核、监控等二级页面。

### 9.2 UI 规范

- 使用 Hertz Design System v1.3.3 的设计令牌、颜色、字体、间距、圆角、阴影和基础组件。
- 结合 UI UX Pro Max 的信息层级、表单可用性、表格可读性、响应式和无障碍原则。
- 页面优先采用“页面标题＋关键操作＋指标＋主任务区＋辅助信息”的企业平台布局。
- 状态不得只依赖颜色表达，必须有文字或图标辅助。
- 支持明亮／深色主题，并在平板和移动端保持主要任务可用。

### 9.3 交互一致性

- 列表页统一提供搜索、筛选、排序、分页、列配置和批量操作。
- 详情页统一呈现基本信息、业务信息、版本、权限、血缘、审计和关联对象。
- 长任务必须显示阶段、进度、当前步骤、预计时间和错误详情。
- 发布、下线、删除、回滚、批量授权等高影响操作必须显示影响范围并进行二次确认。
- 用户完成操作后必须获得成功、失败或部分成功的明确反馈。

## 10. 当前原型已覆盖范围

当前 V0.1 原型已覆盖：

- 平台总览和八个一级模块入口。
- 知识生命周期主链路展示。
- 数据源监控、资源列表、加工流水线、资产列表、图谱分类、知识服务、Agent 场景和运营工单的形态示例。
- 通用导航、搜索、筛选、标签页、弹窗、消息反馈、明暗主题和响应式框架。

当前原型尚未表达完整的二级、三级业务流程，原型中的按钮和指标主要用于展示产品方向，不代表所有后台能力已完成。

## 11. 后续原型深化优先级

### P0：三条核心闭环

1. **知识加工闭环**
   - 新建加工任务。
   - 选择资源和加工模板。
   - 配置流水线节点。
   - 查看执行过程和失败原因。
   - 检查实体、关系、事件和冲突候选。
   - 质量门禁、人工抽检和交付资产中心。

2. **知识资产化闭环**
   - 候选知识审核。
   - 证据对照和冲突裁决。
   - 目录、业务元数据和管理元数据编辑。
   - 权威等级、适用范围和权限设置。
   - 资产发布、版本更新、下线和影响分析。

3. **知识图谱构建闭环**
   - 创建企业级或专题图谱。
   - 本体建模与版本管理。
   - 选择已发布知识资产。
   - 资产到本体的映射。
   - 执行构图、质量校验、人工确认和发布。
   - 图谱可视化、查询、追溯和服务化。

### P1：服务化与应用闭环

- 混合检索策略配置与效果评测。
- API、MCP 和 Skill 创建、测试、授权、发布与监控。
- Agent 的知识选择、工具编排、安全策略、评测和发布。
- 统一语义知识门户和专题应用门户。

### P2：运营与管理完善

- 知识效果指标体系。
- 用户反馈与知识治理工单。
- 成本分析、容量预测和 SLA 管理。
- 租户、组织、用户、角色、审计和系统配置。

## 12. 评审待确认问题

### 12.1 业务与组织

- 首期落地优先选择哪个业务域和哪个闭环场景？
- 知识资产的业务责任人、管理责任人和技术责任人如何分工？
- 资产发布采用几级审核，哪些资产类型可以自动发布？
- 企业统一语义图谱由哪个组织统一管理？专题图谱是否允许业务部门自主发布？

### 12.2 知识标准

- 知识资产的正式类型清单和最小元数据集是什么？
- 权威等级采用几级，评定标准和冲突裁决规则是什么？
- 企业级目录、业务域目录、专题目录和知识包之间如何定义？
- 本体、业务术语和数据标准之间如何对应？

### 12.3 权限与合规

- 源系统权限是完全继承，还是允许在资产层扩大／缩小范围？
- 从多个来源融合的知识资产如何计算最终权限？
- 哪些 Agent 行为必须人工审批？是否允许 Agent 回写业务系统？
- 数据保留、删除、审计和敏感数据处理需遵循哪些行业规则？

### 12.4 技术与性能

- 首期需接入的数据源类型、数量、日增量和实时性要求是什么？
- 文档、实体、关系、向量和图谱的预估规模是什么？
- 检索、图谱查询、API 和 Agent 的 SLA 目标是什么？
- 是否存在私有化、信创、离线网络或指定基础软件要求？

### 12.5 效果验收

- 如何定义知识抽取的准确率、召回率和人工抽检方法？
- 如何建立搜索、RAG、图谱推理和 Agent 的基准评测集？
- 首期验收是以平台功能为主，还是以某个业务场景的效果改善为主？
- 业务效果应采用哪些指标：查找时间缩短、问题解决率、人工工时减少、风险识别率或决策质量提升？

## 13. 评审通过标准

本阶段产品方案建议以下列条件作为评审通过标准：

- 八个一级模块的定位、输入、输出和管理对象已明确。
- “资源—候选知识—知识资产—图谱—服务—应用”的边界无重大歧义。
- 知识加工位于资产化之前，图谱构建优先使用已发布资产的逻辑得到确认。
- 企业统一语义图谱与专题业务图谱的共性工具和差异化管理得到确认。
- 首期业务场景、用户角色、数据范围、权限原则和验收指标得到确认。
- 后续详细原型和 PRD 的优先级、责任人和计划得到确认。

## 14. 详细 PRD 建议模板

后续每个二级功能建议按以下结构编写：

1. 需求背景与业务问题。
2. 目标用户与角色权限。
3. 使用场景与前置条件。
4. 主流程、分支流程与异常流程。
5. 页面信息架构与交互说明。
6. 字段、状态、规则和校验条件。
7. 权限、审批、审计和安全要求。
8. 外部系统、数据和服务依赖。
9. 非功能需求。
10. 验收标准与测试用例。
11. 指标埋点与运营方案。
12. 未决问题、风险和版本变更记录。
