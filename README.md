# 知识工程平台

面向企业知识建设与使用的产品原型，围绕资源纳管、知识生产、知识管理和知识服务，表达从原始资源到知识资产，再到业务使用的产品流程。

当前项目用于验证产品组织、页面交互与业务规则，不代表后端能力、真实权限控制或服务调用已经实现。

## 产品框架

以下为 2026-09-08 讨论整理的产品口径；现有原型中的旧名称与交互按此方向逐步对齐。

| 产品模块 | 核心职责 | 主要内容 |
| --- | --- | --- |
| 资源纳管 | 接入和组织知识原料 | 知识源、文件、数据表、原始图数据、资源目录、元数据标准、标签、接入任务 |
| 知识生产 | 建设、加工和验证知识成果 | 加工模型与流程、加工任务、成果确认、知识库构建、语义知识图谱构建及资产自身发布 |
| 知识管理 | 组织和管理知识资产 | 知识库与语义知识图谱的资产视图、知识资产目录、资产与目录的挂载关系、目录成员与权限 |
| 知识服务 | 将知识能力提供给业务与应用 | 知识服务配置、测试与评估、调用接入与授权、开发者支持 |

工作台提供待办、异常和常用入口；系统配置提供用户、组织、角色与日志等支撑能力。业务门户面向普通业务人员提供搜索、问答、资产浏览、场景助手和反馈，不要求其理解后台建设过程。

产品主线：

`接入资源 → 加工并建设知识库／语义知识图谱 → 资产自身发布 → 挂载知识资产目录 → 配置知识服务 → 业务门户或外部应用使用 → 反馈与更新`

目录关系也可以在资产发布前准备；只有满足发布和权限条件的资产，才对普通使用者提供服务。

## 知识资产与模块边界

平台在知识管理中管理两类知识资产：

- **知识库**：组织文档、知识分段、问答、规则等知识内容。
- **语义知识图谱**：组织实体、关系、事件及其来源证据；企业统一语义知识图谱和专题知识图谱是这一类型下的不同范围与用途。

知识内容是资产内部管理的内容，不与知识库、语义知识图谱并列为本层的资产类型。

知识生产承担资产建设，知识管理承担资产组织。同一个知识库或图谱在两处是不同工作视图，不是两份独立资产。知识资产管理负责目录和挂载关系，不另建一套文件资源管理功能。

## 目录与空间

目录与空间职责合并：目录既组织内容，也承载负责人、成员、协作和管理权限，不额外引入一套平行的空间管理对象。企业、团队、个人可以作为不同的归属与使用范围。

- 知识源说明内容从哪里来、如何同步。
- 目录说明内容如何组织，以及谁负责、谁协作、谁可以管理。
- 元数据与标签描述内容特征和适用范围。
- 资源目录组织原始资源，知识资产目录组织知识库与语义知识图谱；可复用分类标准，但不要求分类体系完全相同。
- 同一资产可挂载多个目录，保持同一内容、版本与发布状态；移除挂载不删除资产。

### 权限设计基线

目录支持成员权限及子目录继承，同时区分目录组织权限、资产使用权限和资产建设权限。

默认情况下，从目录使用资产需要同时具备目录访问权与资产使用权。挂载本身不自动扩大资产授权，目录管理员也不自动获得资产内容编辑权。

添加资产时，可设计“仅建立挂载关系”和“同时授权目录成员使用”两个选项；后者需由具有资产授权权限的人操作，并展示授权范围。具体授权交互待原型细化。

## 发布与目录挂载

**当前采用资产自身发布、目录不重复发布的设计方向。** 资产发布确认可使用的版本，目录挂载提供发现入口，两者不使用同一套操作语义。

| 操作 | 产品规则 |
| --- | --- |
| 创建或调整目录 | 由有目录管理权限的人操作，无须另走发布流程 |
| 挂载已发布资产 | 校验权限后生效，无须重复发布资产 |
| 挂载未发布资产 | 管理端可维护关系并显示未发布状态，普通使用者不可用 |
| 移除挂载 | 仅移除当前目录入口，保留资产及其他目录关系 |
| 取消资产发布 | 各目录中的使用入口同步不可用，管理端保留挂载关系 |
| 发布资产新版本 | 默认跟随当前发布版本，目录关系不变 |

资产侧使用“发布／取消发布”，目录侧使用“添加资产／移除挂载”。目录可见不等于资产已发布或已授权。

若未来企业公共目录需要专人把关，可增加“上架审核”，审核展示范围和目录准入，不重复审核资产内容；当前阶段不增加此流程。

## 知识服务与用户分工

将现有“知识应用”调整为“知识服务”，优先围绕提供什么能力组织产品，而不是将智能体、协议与开发工具平铺为同级能力。

| 建议入口 | 职责 |
| --- | --- |
| 服务管理 | 配置知识检索、知识问答、图谱查询等服务，明确资产范围、用途、使用方与可用状态 |
| 测试与评估 | 验证检索结果、回答效果、来源证据与适用范围 |
| 接入与授权 | 管理调用方与 API、MCP 等开放方式 |
| 开发者支持 | 提供接口文档、SDK 与接入示例 |

API、MCP 是服务接入方式，SDK 是开发支持。技能管理是否独立保留，取决于是否有明确的可复用业务动作场景，暂不以预留菜单代替产品定义。

| 用户角色 | 主要工作 |
| --- | --- |
| 普通业务人员 | 使用搜索、问答与场景助手，提交反馈 |
| 业务专家／知识负责人 | 确定知识范围，提供标准问题与答案，确认内容并验证业务效果 |
| 知识工程师／资产建设人员 | 配置加工与构建过程，整理和维护知识库、图谱 |
| 目录管理员 | 组织目录、维护成员及挂载关系，在授权范围内协作 |
| 应用配置人员／开发人员 | 配置服务、工具与流程，测试并发布使用能力 |

完整智能体构建不作为普通业务人员的默认任务。当前优先采用知识服务配置；需要问答助手时，可提供“填写用途 → 选择资产 → 设置回答规则 → 试问 → 发布”的模板化入口。专业智能体构建是否作为独立入口，后续按明确需求决定。

## 原型现状与后续对齐

上述规则是产品设计基线，不代表所有页面已经同步实现。本次仅整理文档。

优先对齐：

1. 统一导航口径为“资源纳管、知识生产、知识管理、知识服务”。
2. 将知识资产管理页对齐为资产目录与知识库／图谱的挂载管理，清理文件管理语义。
3. 区分资产自身发布与目录挂载，明确未发布、取消发布和多目录挂载状态。
4. 细化目录继承、资产使用权限以及挂载时的授权提示。
5. 将知识应用的现有占位入口按知识服务方向整理，再补测试、接入与业务门户的衔接。

后续以一个完整业务案例验证：新版制度接入、知识加工与确认、知识库版本发布、目录发现、服务引用、业务反馈与更新。
